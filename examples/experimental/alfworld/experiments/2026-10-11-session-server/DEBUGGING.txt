Incidents, diagnosis and resolution
-----------------------------------
A. Early tool-parser failure: the first attempted evaluation did not have the
   correct explicit reasoning/tool-call parser pair. That attempt is archived
   as attempt-1-invalid-tool-parser.log and is excluded from the baseline.
   The SSOT parser flags above corrected collection; native session requests
   and terminal environment rewards were verified afterward.
B. Initial eval upload at topology transition: token metrics had arrived but
   the standard eval dictionary was not yet visible after the old job stopped.
   Replayed the exact persisted standard eval dictionary once into the same
   W&B run, preserving eval/step=0. No recomputed or fabricated scores.
C. W&B URL: Forge returned Run not found when the project separator '&' was
   URL-encoded as %26. User-facing links retain the literal '&'. SDK-generated
   encoded redirects should not be used as proof a run is missing.
D. W&B summary can lag history / reflect a stale value in this shared run.
   Verified eval with scan_history instead. Step-25 standard and custom eval
   records exist in history (_step 131 and 130); do not replay them simply
   because summary still shows the baseline.
E. Live logging update: editing the file alone does not reload a cached Python
   module. Retrieved the existing RolloutExecutor handle through the named
   RayWorkerManager's get_worker_infos/get_actor_handle APIs, and used Ray's
   DeveloperAPI __ray_call__ to reload only the diagnostics module. Verified
   in actor pid61026 at rollout_id8, without restarting training.
   A preliminary auxiliary-driver attempt to call core_worker.get_actor_handle
   directly on an unregistered ID aborted that auxiliary process; it did not
   stop the training job. Do not use that private shortcut.
F. Environment collection repeatedly timed out on git diff after 10 seconds
   on the Volume. Tracebacks belong to optional provenance collection, not the
   optimizer or eval. Retained logs and checked actual job/step progress.
G. One inference worker's startup /freeze_gc request raced its HTTP listener
   and got ConnectionRefused. Subsequent health and generation calls returned
   200, all four inference engines served requests, and training proceeded.
H. TileLang dk_fragment warning during first backward kernel compilation:
   inspected flash_qla/.../hopper/fused_bwd.py. The read is guarded by i_s>0;
   a previous loop iteration initializes the fragment via GEMM clear_accum.
   No library patch or disabling of compiler checks was made. Subsequent
   optimizer outcomes were NORMAL with finite loss and gradient norms.
I. GPU health: volatile and aggregate uncorrectable ECC counters were zero.
   GPU6 had two historical corrected SRAM errors, with current volatile count
   zero. The W&B 'Uncorrected Memory Errors' chart title alone was not evidence
   of an error. No device-repair flag was observed during inspection.
J. Training rewards fluctuated between batches: reward = float(env.infos['won']),
   so raw_reward is binary episode success averaged over 4 prompt groups x 8
   trajectories. Audited the first 416 episodes against terminal metadata and
   W&B; all matched. Their combined success was 238/416=57.21%. A single batch
   of 27/32=84.375% is not a fixed-eval result.
K. Persistence and capacity: a step-25 full distributed checkpoint occupies
   about 58.9 GB, while the Mac has roughly 12 GiB free. The user explicitly
   permits cloud checkpoint storage. Keep weights and all raw run artifacts on
   the persistent Volume, verify them independently of the Sandbox, and make
   local backups of lightweight code/logs/results/manifests. Do not delete the
   Volume when releasing the GPU container.

Archive conventions
-------------------
Recorded operational scripts may be saved as .py.txt snapshots to preserve the
exact environment-specific commands, including fixed paths. They are execution
provenance, not additional reusable launchers. Use the maintained launcher for
new experiments. Credentials are injected separately; no credentials belong in
this repository or the public archive. Logs are scanned/redacted before local
or Git publication. Large checkpoints and rollout dumps stay on the Volume;
file lists, sizes, hashes and recovery instructions are committed instead.
